# CardForge 架构说明

## 当前边界

CardForge 采用三层很薄的结构：

```text
平台 app
  ├─ core/games：注册、清单、异步装载契约
  ├─ shared：不带规则的视觉与设备能力
  └─ games/<game-id>：某一游戏完整的规则、状态、AI 和 UI
```

依赖只向 `core` / `shared` 方向流动。一个游戏不能导入另一个游戏的实现；平台也不能根据某个游戏的 HP、阵营或卡牌类型做判断。

### core

`GameManifest` 是大厅可读取的元数据，`GameRuntimeProps` 是平台传给游戏的最小生命周期接口，`GameRegistry` 负责去重与检查可玩游戏是否提供加载器。注册项通过动态 `import()` 加载，因此新增游戏不会自动进入首屏包。

游戏存档只通过 `GamePersistenceHandle` 流转：平台提供带 `schemaVersion` 的 localStorage 信封（`GameSaveStore`），只读写字节、不解读内容；序列化、结构校验与版本判定全部由游戏自己的 `domain/persistence.ts` 负责。平台因此仍然不认识任何游戏状态。

大厅的首推位、牌桌字符与标语由 manifest 的 `featured` / `mark` / `tagline` 提供。平台不认识任何具体游戏 ID：没有游戏声明 `featured` 时退回第一个可玩游戏，一个可玩游戏都没有时只是不渲染首推卡片，而不是崩溃。

### app / GameHost

`App` 只解析大厅与当前游戏 ID，并通过 `?game=<id>` 同步浏览器历史。只有注册为 `playable` 且提供 loader 的 ID 才能恢复；从大厅进入游戏会创建历史项，浏览器返回键和游戏内退出都会回到大厅。URL 处理是纯函数并独立测试，不需要引入路由框架。

`GameHost` 统一提供动态模块的 Suspense 加载状态和 Error Boundary。某个游戏的 chunk 加载失败或 React 渲染异常时，只替换为该牌桌的恢复页。渲染异常会本地重建 lazy loader 和错误边界；动态 import 网络失败则保留当前 `?game=` 入口并刷新页面，以清除浏览器缓存的模块失败状态。它不理解游戏状态，也不接管游戏内重开、AI 或回合。

大厅通过 `GameSaveStore.loadGameSave` 读取**信封级别**的存档信息（`savedAt`、`revision`）生成「继续牌桌」，仍不触碰 `snapshot.data`；因此平台可以在不引入任何玩法假设的前提下提供断点续玩入口。

### shared

`CardFrame` 只提供卡片的几何、排版、选中与禁用状态。它不知道费用、伤害、颜色匹配或点数。`ParticipantIdentity` 只描述身份和控制者，不假设玩家拥有生命值。声音服务只接受抽象提示音，延迟创建并复用一个 `AudioContext`，声音开关保存在本机且可跨标签同步。`usePlaybackSpeed` 是新增的共享演出节奏偏好：只负责 1× / 2× / 4× 的读取、循环切换与跨标签同步，三张牌桌用 `playbackDelay` 把各自的 AI 基础间隔换算成实际等待时间，规则层不受影响。存档服务只读写信封（`schemaVersion` + 快照），损坏、版本不符或存储不可用时静默降级，从不尝试修复游戏内容。`useModalFocus` 负责弹层的初始焦点、Tab 约束、Escape 关闭和焦点恢复，不理解弹层中的游戏内容。

只有确认被多种游戏共同需要、且不引入玩法假设的能力，才应移入 `shared`。

### games/ember-pact

Demo 自己拥有：

开局在战术炉谱里选择出战角色：四人任选其一，其余交给本地 AI，敌我分组随所选角色的阵营翻转，UI 不假设人类固定属于某一阵营。四套牌各 18 张，共用接近的攻防、救援和响应骨架，再以特色牌与被动形成防守反击、治疗支援、破盾强攻和灼烧追击四种定位。

- `domain/data.ts`：角色与卡牌数据；
- `domain/engine.ts`：抽牌、行动力、合法目标、响应、效果解析、归队、回合、退场与胜负；
- `domain/ai.ts`：只属于本游戏的三档评分式决策，不调用网络或外部 API；
- `domain/session.ts` / `persistence.ts`：游戏偏好、活动对局、本机战绩、版本校验与旧存档迁移；
- `EmberPactGame.tsx`：交互编排和 AI 动画节奏；
- `components/` 与样式：HP、护盾、战场和手牌表现。

规则引擎是纯函数。每席通常有 2 点行动力并最多打出 1 张进攻牌；可响应的攻击会进入独立的卸力窗口，响应结束后回到原行动者。UI 只发送 `playCard` / `respondToAttack` / `endTurn` 意图并渲染返回的新状态，不直接修改 HP。卡牌效果由数据中的 `effects` 数组描述，再交给效果处理器解析；被动、状态、联携、援护归队、残局过载和抽牌溢出都会产生结构化 `ResolvedEvent`，战报、AI 评分、统计和动画消费同一份结算结果。响应窗口复用 AI 的 `predictedIncomingDamage` 展示预计损失；仍有可出牌时结束回合会弹出确认层。本机战绩记录弃局数并支持在无活动对局时清空。

牌库抽空时按状态中的 `rngSeed` 重新洗牌，而不是把弃牌堆原样倒回。洗牌发生在回合推进内部，用状态携带的种子而非注入的随机函数，规则层因此仍是纯函数，长局的抽牌顺序也不会退化成固定循环。

争焰的活动局与长期档案使用游戏内 schema v2；损坏的活动局不会抹掉有效战绩，未知的未来版本也不会被自动覆盖。固定种子的批量模拟作为平衡基线，负责暴露阵营胜率、异常长局和无法结束的状态，但不进入平台 Core。

### games/twenty-one

第二款可玩游戏验证了平台边界：它没有复用「争焰」的战斗状态或回合管理，而是在自己的 `domain` 内定义多副牌靴、Ace 点数、保险、逐手行动、庄家步骤和聚合结算。随机函数由创建入口注入，因此规则可以确定性测试；庄家每次只推进一个状态步骤，React 层只负责安排步骤间隔、声音与动画。

局面循环由筹码驱动：每轮先进入 `betting` 押注，玩家可以要牌、停牌、加倍、分牌或迟投降；庄家明牌为 A 时先处理保险。每个分牌手独立托管下注并按索引行动，最后由一个结构化 settlement 统一计算逐手结果、保险和总净输赢。房规、经典/挑战会话、策略提示与长期统计都留在 `games/twenty-one`，平台只保存该游戏提供的版本化快照。最近一次下注记录在 `preferences.lastBet` 中（旧存档缺省时兼容恢复），用于「重复上一注」快捷按钮。

房规采用预设加关键开关：牌靴数、S17/H17、Blackjack 赔率、分牌上限、DAS、A 的再分/补牌、保险与迟投降均可配置。默认六副标准桌；挑战模式锁定标准桌以保证本机成绩可比较。基础策略提示也是游戏内纯函数，只返回当前合法动作与解释，不调用网络服务。牌桌册新增「记录」页签展示本手最近 20 条事件，模式选择页把各挑战的无辅助/辅助通关记录直接印在卡片上；不可用决策按钮通过 `title` 给出原因。

标准扑克牌面也保留在游戏内。它的花色、点数和暗牌并不是所有 CardForge 游戏都具有的通用概念，暂不扩充 `shared/CardFrame`。这次新增只改动了注册清单和大厅的多可玩游戏展示，没有修改「争焰」实现或 Core 契约。

### games/guandan

第三款可玩游戏拥有自己的双副牌、级牌、百搭、牌型比较、跟牌、清墩、出完顺序和组队胜负。`domain/ai.ts` 只消费本游戏的合法牌型生成器；React 仅负责安排四个座位的行动间隔、选牌和托管，不在组件中改写手牌或回合。AI 不压对家的牌墩，但当某一手能直接打空自己的手牌时例外——出完牌永远推进本队的胜负。对手 AI 分三档：见习在较优候选中带确定性抖动，标准沿用基础牌力启发式，战术额外保护百搭、规划收尾，并且只有炸弹能压时会在对手逼近走完前选择过牌；难度作为牌局状态的一部分写入存档。

级牌不再固定为 2：`MatchState` 记录双方级别、局数与本局打谁的级，`levelRank` 取自打级方的当前级别。胜方是头游所在队，与哪一队先走空无关；升几级由头游队友的名次决定（双下 3 级、三游 2 级、末游 1 级），级别封顶在 A，只有在 A 上再赢一局才算打过 A 赢下整场。

**`MatchState` 刻意留在 `games/guandan/domain` 内，没有进入 Core。** 这是本轮最值得记录的一次边界检验：跨局状态第一次真实出现，但它只服务掼蛋的升级规则——二十一刻的筹码与牌靴、争焰的单场对局都不共享这个语义。等到第二款游戏出现语义一致的「一场比赛」概念时，再讨论提取。

「掼蛋」和「二十一刻」都画扑克牌，但前者需要双牌标记、王、级牌百搭和 27 张紧凑手牌，后者需要暗牌和大号点数表现。当前只共享最小 `CardIdentity`，保留两套游戏内牌面；相同花色不等于相同领域模型。若第四款游戏再次产生一致的洗牌或牌面需求，再提取无规则假设的扑克牌工具。

牌型刻意只实现单张、对子、三张、三带二、五张顺和四张起炸，百搭是当前级牌的红心。连续升级已经补上，进贡还贡、木板/钢板和同花顺炸弹仍留给后续迭代，都不进入平台 Core。

### games/dingding

第四款可玩游戏是原创身份阵营暗局，作为“三国杀-like 标准身份局”的 M2 规则骨架。四位玩家随机获得主君、辅臣、叛锋、流谋四种身份与一名不重复的原创武将：主君公开且体力 +1；主君方需要清剿叛锋与流谋，叛锋在主君倒下时胜利，流谋必须成为主君倒下时唯一的其他存活者。

领域层完全留在 `games/dingding`：`data.ts` 定义原创牌堆（刺击/闪避/疗元、聚势/拆解/牵袭/无懈可击/约斗/合围/齐射/同袍/刺探、延时牌断锋/困阵/焚营、援护、长锋/穿云/连机弩/犀甲/赤影/磐影），`heroes.ts` 定义 20 名原创武将（3/4 基础体力，覆盖强命、多刀、直伤、爆发、控制、续航、辅助等定位）及其触发点配置，`engine.ts` 实现回合阶段机、距离与攻击范围、装备替换、刺击响应窗口、伤害与濒死求桃、身份揭示与数据表驱动的胜负奖惩。武将技能是数据驱动的最小框架：`TriggerPoint`（回合开始/结束、造成/受到伤害、进入濒死、锦囊结算完成）加被动距离修正，引擎在对应位置调用 `runSkillTrigger`，一次性技能标记写入 `player.skillFlags` 并在回合结束时清空（坚壁的减伤标记持续到拥有者下个回合开始）。M3 已加入可选技能的玩家决策帧：破军、坚壁、青囊、潜行、突袭、余烬、洞彻、秉笔，夜枭提供回合开始摸牌；后续武将池扩展到 20 名：璇玑带摸弃循环、金玉在他人死亡时摸牌、乐姬死亡时沉默伤害来源；烈骁提供必中刺击、武锋重置出杀次数、冲阵与游缴/军师提供直伤和控制、豪客提供摸三爆发、磐卫与辅弼补齐续航和辅助，它们像锦囊一样进入结算栈（`PendingSkill`），由技能拥有者选择消耗与目标或放弃发动。M3 也加入判定区与 `PendingDelayed` 判定帧：断锋/困阵/焚营在判定阶段翻开牌堆顶牌结算，回合流程为准备 → 判定 → 摸牌 → 出牌 → 弃牌。身份奖惩已补全为纯函数表：击退叛锋摸 3、流谋不取奖惩、主君误杀辅臣弃光手牌；主君倒下立即终局，不再走叛锋摸 3 的装饰性奖励。M4 已加入见习/标准/战术三档 AI 难度并写入牌局状态：标准与战术档使用 `identityBelief` 身份信念选择目标，见习档行动更保守。规则层新增辅臣护主（存活辅臣可弃 1 张手牌为主君抵挡 1 点刺击伤害）：主君未闪避刺击时压入 `PendingProtect` 决策帧，由辅臣选择是否公开身份并弃牌；第 24 轮起的非致死过载用于压缩无限回血拉锯。M5 体验层已开始：开局人类玩家从三名武将中三选一，AI 从剩余武将补位；牌桌中央会以层叠 chips 展示当前结算栈，结果页显示本局难度并带关键节点/完整记录复盘；存档升级为长期档案 + 活动牌局（schema v8），战绩面板展示身份与武将胜率。`scripts/dingding-balance.ts` 以固定种子跑全 AI 对局，输出三方胜率、回合与决策分布、身份退场、卡牌使用、主动技发动和延时牌判定次数；它负责暴露平衡漂移与异常长局，同样不进入平台 Core。

状态中的 `stack` 是结算栈：锦囊打出后压入 `trick` 帧并按座位顺序询问「无懈可击」；无懈本身也是 `trick` 帧，可被另一张无懈反制。询问被反制链挂起时帧标记 `awaitingResponse: false`，链尾结算后自栈顶连续结清被抵消或就绪的帧；约斗与群体锦囊结算时在栈顶生成 `duel` / `horde` / `volley` 帧逐人响应，期间触发的 `dying` 帧压在这些帧之上，救回或退场后再继续原结算。拆解/牵袭可作用于手牌、装备或判定区，使装备与延时牌不再不可反制；刺探猜测身份成功会公开目标并摸两张牌，失败由使用者弃牌。退场者的手牌与装备进入弃牌堆，避免长局在 1 对 1 对角座位时永远卡死。`persistence.ts` 校验身份唯一性、武将 id、牌堆守恒、帧引用与阶段不变量，当前存档 schema 为 v8，更早版本按可读性迁移或拒绝，而非猜测修复。

M3 的 8 个主动技与延时锦囊判定帧已经以“结算栈 + 技能触发点”的方式在本游戏内建模，不会进入 Core。

## 新增一个游戏

1. 创建 `src/games/<game-id>/`，让该目录完整拥有自己的状态、规则、AI 和 UI。
2. 导出一个满足 `GameRuntimeProps` 的 `Game` 组件。
3. 在 `src/games/registry.ts` 中加入 manifest 和动态加载器。
4. 需要断点续玩时，在 `domain/persistence.ts` 里提供 `serialize` / `restore`（含结构校验）与 `schemaVersion`，组件里通过 `persistence` 句柄恢复初始状态、自动存档并在重开时清除。
5. 为规则层编写纯函数测试，并验证 390px 竖屏、常见笔记本矮屏和宽桌面布局。

如果新游戏需要 UNO 式颜色匹配或 Blackjack 式庄家流程，应直接在新游戏内定义这些概念，而不是扩充平台 `GameState`。只有多个游戏真实出现语义一致的重复能力，再考虑提取共享模块。

## 第一阶段刻意不做

当前没有通用技能 DSL、联网同步、持久化账号、商城、复杂事件总线或跨游戏存档格式。这些能力需要明确产品需求来验证边界，现在加入只会让最小契约变重。

四款游戏补齐核心循环后，跨局状态持续出现（掼蛋的级别、二十一刻的筹码、定鼎的身份局牌桌），此前只在内存中、刷新即重来。现在它们通过 `GamePersistenceHandle` 在本机断点续玩：掼蛋的升级进度、二十一刻的筹码与牌靴、争焰进行中的对局、定鼎的牌局都会在刷新后自动恢复，重开或整场结束才清除。存档仍是**游戏层格式**——每款游戏的 `domain/persistence.ts` 定义自己的序列化与结构校验，平台信封不解读内容；账号同步、云存档仍然刻意不做。

## 框架引入阈值

2026-08 的架构审查决定暂不引入 XState、boardgame.io、Phaser 或 Colyseus。当前 Core 只负责注册和加载；四款游戏各自的回合、合法行动与 AI 仍是可测试的小型纯函数模块。

- **XState**：同一个平台 Session 同时需要存档恢复、暂停、重连、观战或错误重试中的至少两项时，再用于 `app/session` 或 `core/session`；不管理具体游戏规则。
- **boardgame.io**：某一新游戏真实需要复杂阶段、同时行动、隐藏玩家视图、撤销/回放或服务端回合验证时，只在该游戏内部做适配试验；不成为 CardForge 唯一引擎。
- **Phaser**：某一游戏必须使用大量精灵、摄像机、粒子、Shader 或持续帧循环时，才在该游戏的动态加载模块内部使用。
- **Colyseus**：确认真人联网产品需求并建立权威服务端后再评估；平台 Core 不直接依赖网络框架。

第三款可玩游戏完成后，最小契约经受住了进一步检验：四款游戏真正复用的仍是动态加载、宿主错误隔离、声音提示、倍速偏好、存档信封和基础身份类型，并未出现语义一致、值得提取的通用回合、状态、动作或 AI 调度模型。定鼎的结算栈与技能触发点同样是游戏内概念，继续避免凭预想向 Core 增加这些抽象。

## 验证策略

验证按边界分层，不把浏览器测试当作规则引擎测试的替代品：

- 游戏 `domain` 继续使用 Vitest 覆盖洗牌、合法行动、效果结算、AI 决策和胜负等纯函数；
- 游戏的 `persistence` 层覆盖序列化/恢复 round-trip 与损坏存档拒绝，存档服务覆盖信封读写与存储不可用时的静默降级；
- React 组件测试覆盖 GameHost 恢复与共享声音服务等独立 UI 能力；
- Playwright 从真实大厅入口验证动态加载、规则弹层、关键操作、键盘交互、声音偏好、刷新续玩和三档响应式视口；
- ESLint 启用 `eslint-plugin-react-hooks` 的 React Compiler 规则集，除经典的 hook 规则外还包括 `set-state-in-effect`、`static-components`、`refs` 等；各款游戏的“思考中”标记因此改为渲染期派生，不再用 effect 写状态；
- GitHub Actions 在主分支推送和拉取请求上依次执行 lint、类型检查、单元测试、生产构建、争焰与定鼎平衡基线，以及浏览器测试。

全仓仅有两处规则豁免，均在源码中写明原因：`GameHost` 的 `static-components`（重建懒加载组件正是重试机制本身）与同一处的 `exhaustive-deps`（`attempt` 是缓存键而非读取值）。

E2E 只观察用户可见角色、名称和状态，不依赖规则层内部数据，也不向业务组件添加测试专用分支。失败时保留截图、视频、trace 和 HTML 报告；正常产物不进入版本库。
